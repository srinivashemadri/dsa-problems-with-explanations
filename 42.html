LeetCode 42 — Trapping Rain Water

Step 1 — Problem Statement

Input: An array of non-negative integers height, where each element represents the height of a vertical bar with unit width. The bars stand next to each other, and rain falls on top of them.

Output: Return the total amount of water that can be trapped between the bars after raining.

Key Constraints: The bars have unit width, water can only stay above a bar if there is a taller boundary on both sides, and the trapped water above any index is determined by the shorter of the tallest bar on the left and the tallest bar on the right.

Edge Cases: An empty array, a single bar, two bars, all bars equal, strictly increasing heights, strictly decreasing heights, and very large heights that can push the total water close to integer limits.

The real question is not “how much rain falls,” but “for each position, how much water can be held above it before spilling over the shorter side?”

Step 2 — Problem Understanding & Approach Overview

This problem is really asking you to compute, at every index, the water level allowed by the best left boundary and the best right boundary, then subtract the bar height itself.

The core algorithmic challenge is to avoid recomputing left and right maxima again and again.

Category: Array, prefix/suffix reasoning, two pointers.

Mental model: Imagine every index as a bucket. The bucket fills only up to the smaller wall on either side. If one side is missing or too low, water escapes.

Subtle trap: Many candidates try to use only the global maximum or only one side’s maximum. That fails, because the water level at an index depends on both sides, not just one.

Step 3 — Brute Force Solution

For each index, scan left to find the highest bar on the left and scan right to find the highest bar on the right. The trapped water at that index is: 

max(0, min(leftMax, rightMax) - height[i])

Sum this for every index. 

for each index i:
    leftMax = 0
    rightMax = 0

    scan from 0 to i:
        update leftMax

    scan from i to n - 1:
        update rightMax

    waterAtI = min(leftMax, rightMax) - height[i]
    if waterAtI > 0:
        add waterAtI to answer

Time Complexity: O(n²). For each of the n positions, we may scan the array twice.

Space Complexity: O(1). No extra arrays are used.

Bottleneck: Repeated scanning of the same prefixes and suffixes.

Step 4 — Intuition Building

Test Case 1

Input: 0 1 0 2
Index 0 and 1 cannot trap anything meaningful at the start.
Action: At index 2, left boundary is 1, right boundary is 2, so water level is min(1, 2) = 1.
Result: Water above index 2 = 1 - 0 = 1.

Test Case 2

Input: 4 2 0 3 2 5
At index 2, left max is 4 and right max is 5, so the level is min(4, 5) = 4.
Action: Water above index 2 = 4 - 0 = 4. At index 3, level is min(4, 5) = 4, so water = 4 - 3 = 1.
Result: This index-by-index view shows why both sides matter.

Test Case 3 (Edge Case)

Input: 5 4 3 2 1
Strictly decreasing array. There is no right boundary taller than the current bars.
Action: Every index leaks to the right.
Result: 0 trapped water.

The key insight is that you do not need to know the whole future at every step if you can maintain enough information about the best left and right boundaries. That is exactly what prefix/suffix maxima and, later, two pointers exploit.

Signal for future problems: When a value at position i depends on the best thing seen on the left and the best thing seen on the right, think prefix/suffix maxima or two pointers immediately.

Step 5 — Optimized Solution 1 (Intermediate)

The first optimization is to precompute the tallest bar seen so far from the left and from the right. Then each index can be answered in O(1). 

leftMax[i] = max(height[0..i])
rightMax[i] = max(height[i..n-1])

for each i:
    waterAtI = min(leftMax[i], rightMax[i]) - height[i]
    if waterAtI > 0:
        add to answer

What is eliminated: The repeated left and right scans for every index.

Time Complexity: O(n). Build two arrays in linear time, then one final pass.

Space Complexity: O(n). Two auxiliary arrays store prefix and suffix maxima.

Step 5 — Optimized Solution 2 (Best Known / Fully Optimal)

The fully optimal solution uses two pointers and constant extra space. The main insight is this: when leftMax <= rightMax, the water at the left pointer is already fully determined by leftMax, because the right side is guaranteed to be at least as tall as leftMax at that moment. So we can safely process the left side. Symmetrically, when rightMax < leftMax, process the right side.

Algorithm name: Two Pointers with Running Maxima.

C++17 Code:

long long trap(vector<int>& height) {
    int n = (int)height.size();
    int l = 0, r = n - 1;
    int leftMax = 0, rightMax = 0;
    long long ans = 0;

    while (l <= r) {
        if (leftMax <= rightMax) {
            leftMax = max(leftMax, height[l]);
            ans += (leftMax - height[l]);
            ++l;
        } else {
            rightMax = max(rightMax, height[r]);
            ans += (rightMax - height[r]);
            --r;
        }
    }

    return ans;
}

Why this works: The smaller boundary decides the water level for that side. If the smaller boundary is on the left, then no future bar on the right can reduce the fact that the current left position is capped by leftMax. So the left cell can be finalized immediately.

Why not always move the taller side? Because the taller side is not the limiting factor. The limiting factor is always the smaller of the two maxima.

Dry Run on a Meaningful Test Case

Input: 4 2 0 3 2 5

Initial State:
l = 0, r = 5, leftMax = 0, rightMax = 0, ans = 0

Step 1: leftMax <= rightMax is true
Pivot side: left
Update leftMax = max(0, 4) = 4
Water added = 4 - 4 = 0
Move l to 1

Step 2: leftMax <= rightMax is false, so process right
Update rightMax = max(0, 5) = 5
Water added = 5 - 5 = 0
Move r to 4

Step 3: leftMax <= rightMax is true
Update leftMax = max(4, 2) = 4
Water added = 4 - 2 = 2
Move l to 2

Step 4: leftMax <= rightMax is true
Update leftMax = max(4, 0) = 4
Water added = 4 - 0 = 4
Move l to 3

Step 5: leftMax <= rightMax is true
Update leftMax = max(4, 3) = 4
Water added = 4 - 3 = 1
Move l to 4

Step 6: leftMax <= rightMax is true
Update leftMax = max(4, 2) = 4
Water added = 4 - 2 = 2
Move l to 5

Final Result: 7

How the Extreme Edge Case is Handled

Input: 5 4 3 2 1
On every step, the right side is the limiting side, but there is never a useful basin because the heights keep decreasing. The algorithm still works because each step finalizes the smaller side and adds zero water whenever the current bar is the boundary itself.

Time Complexity: O(n). Each pointer moves at most n times, and every operation inside the loop is O(1).

Space Complexity: O(1). Only a few variables are used.

Final Interview Insight

If you see a problem where each position depends on the best seen so far from both directions, the pattern is often: first think prefix/suffix maxima, then compress it into two pointers if the comparison logic allows it.

The hidden intellectual move in this problem is realizing that you do not need to know the exact future boundary at every index; you only need to know which side is currently the bottleneck.
