Dijkstra’s Algorithm — Very Detailed Intuition, Mechanics, and Correctness
Step 1 — Problem Statement

Input: A weighted graph is given with nodes and edges. Every edge has a cost, and all edge weights are non-negative. You are also given a source node src. The task is to find the minimum cost from src to every other node, or to a particular destination node if one is specified.

Output: For each node, return the shortest distance from src. If a destination node is unreachable, its distance remains infinite, and in a single-destination version we return -1.

Key Constraints: The graph may be large, so the algorithm should be efficient. The edge weights are non-negative, which is the one crucial condition that makes Dijkstra valid. Distances may become large, so long long should be used for safety. The graph may be directed or undirected; the logic is the same as long as weights are non-negative.

Edge Cases: The subtle cases are a graph with one node, disconnected components, zero-weight edges, multiple edges between the same pair of nodes, and very large path sums. A negative edge is not just a corner case; it breaks the core greedy guarantee, so Dijkstra is not correct in that setting.

Step 2 — What Dijkstra Is Really Doing

Dijkstra’s algorithm is not “just a shortest path algorithm.” At a deeper level, it is a best-first exploration strategy. It repeatedly asks a very specific question:

Among all nodes whose shortest distance is not yet finalized, which one currently looks cheapest from the source?

The algorithm answers that question using a min-heap priority queue. The heap always gives the node with the smallest tentative distance next. That is the core idea. The moment you understand that, the rest of the algorithm becomes a sequence of careful bookkeeping steps.

The mental model is this: imagine the source node dropping ripples into a pond. Every edge spreads that ripple with a cost. The cheapest ripple to reach a new node should be expanded first, because any more expensive route to that same node cannot lead to a better answer once cheaper routes are already available. That is the greedy heart of the algorithm.

The subtle trap is thinking “the first time I see a node, I can lock it.” That is false in weighted graphs. You may discover a node early through an expensive route and later discover a cheaper route. Dijkstra handles this by storing tentative distances and only finalizing a node when it is removed from the heap with the smallest known cost.

Step 3 — Brute Force Intuition Before Optimization

Before Dijkstra, it helps to understand what the brute-force mind would try. A naive approach would enumerate all paths from the source and take the minimum cost among them. That is conceptually simple but disastrously expensive because the number of possible paths can explode exponentially.

Brute Force Idea

function dfs(node, cost):
    if node is destination:
        update answer
        return

    for each outgoing edge (node -> next, weight):
        if next is not already on current path:
            dfs(next, cost + weight)

This fails at scale because it explores paths, not states. Dijkstra changes the perspective: instead of exploring all paths, it explores each node in the order of cheapest known access cost. That one shift is the entire breakthrough.

Step 4 — Intuition Building Through Small Test Cases

Test Case 1 — Single Direct Edge

Input: 0 --5--> 1, source = 0

    There is only one possible way to reach node 1.
    The tentative distance to node 1 becomes 5 immediately.
Action: Push (0, 0) into the heap, pop it, relax edge 0 → 1, and set dist[1] = 5.
Result: Shortest distance to node 1 is 5.

Test Case 2 — Two Competing Routes

Input: 0 --2--> 1, 0 --5--> 2, 1 --1--> 2, source = 0

    Node 2 is first discovered with cost 5 through 0 → 2.
    But later a better path appears: 0 → 1 → 2 with cost 3.
Action: The heap processes node 1 before node 2 because 2 is smaller than 5. That allows the cheaper route to node 2 to overwrite the older expensive one.
Result: dist[2] becomes 3, not 5.

Test Case 3 — Unreachable Node

Input: 0 --1--> 1, node 2 isolated, source = 0

    Nodes 0 and 1 are reachable, but 2 never appears in the heap.
    The algorithm finishes when the heap becomes empty.
Action: Continue until no more reachable states exist.
Result: dist[2] stays infinite, meaning unreachable.

These tiny cases show the pattern. The heap is not just an implementation detail; it is the mechanism that lets the algorithm always expand the currently cheapest frontier first. That is why Dijkstra works so well for non-negative weights.

The signal that should immediately make you think of Dijkstra is this: “Find the cheapest way to reach something in a graph, and all edge costs are non-negative.”

Step 5 — The Core Invariant and Why It Is True

This is the most important part of the algorithm.

Invariant: When a node is removed from the min-heap with distance d, and d equals the current recorded distance for that node, then d is the true shortest distance from the source to that node.

Why is this true?

Suppose the heap pops node u with tentative distance d. This is the smallest tentative distance among all nodes not yet finalized. If there were some shorter path to u that we had not yet discovered, then that path would have to pass through some intermediate node x. Because all edges are non-negative, the tentative distance to x would have to be less than or equal to the final distance to u. But then x should have been popped before u if it were truly cheaper. That contradiction is the greedy proof idea.

Notice how critical non-negative weights are. If negative edges existed, a node that looked finalized could later be improved by going through a negative edge. That would break the invariant completely.

Why we do not need to revisit finalized nodes: Once the shortest distance of a node is fixed, any alternative route would have to go through another node that is not cheaper than the one already chosen. With non-negative weights, such detours cannot produce a smaller total cost.

Step 6 — Step-by-Step Mental Simulation of the Heap

Take this graph:

0 -> 1 (2)
0 -> 2 (5)
1 -> 2 (1)
1 -> 3 (7)
2 -> 3 (2)

Start with:

dist = [0, INF, INF, INF]
heap = (0, 0)

Iteration 1:
Pop (0, 0). This means node 0 is currently the cheapest reachable unfinished node.
Relax outgoing edges:
  0 → 1 gives dist[1] = 2
  0 → 2 gives dist[2] = 5
Heap now contains: (2, 1), (5, 2)

Why this matters: We have not “chosen the final route” to nodes 1 and 2 yet. We only know the cheapest route found so far. The heap preserves candidates in ascending order of cost.

Iteration 2:
Pop (2, 1). Node 1 is now finalized because it is the cheapest remaining candidate.
Relax outgoing edges:
  1 → 2 gives a new cost 2 + 1 = 3, which improves dist[2] from 5 to 3
  1 → 3 gives dist[3] = 9
Heap now contains: (3, 2), (5, 2 stale), (9, 3)

Important observation: Node 2 was already present in the heap with cost 5, but that entry is now stale. We do not delete it manually. We simply allow it to stay there and skip it later when it comes out.

Iteration 3:
Pop (3, 2). This is better than the old 5, so node 2 is finalized at cost 3.
Relax outgoing edge:
  2 → 3 gives a new cost 3 + 2 = 5, which improves dist[3] from 9 to 5
Heap now contains: (5, 2 stale), (9, 3 stale), (5, 3)

Iteration 4:
Pop (5, 3). If 3 is the destination, we can stop immediately.
The shortest distance is 5.

This dry run reveals the exact logic of the heap. It is not storing final answers. It is storing best-known candidates, and the algorithm keeps correcting itself until the cheapest candidate for each node is confirmed.

Step 7 — Why the “Stale Entry” Trick Is So Important

There is a very common beginner confusion: “Why is the same node inserted multiple times?” Because Dijkstra is usually implemented without decrease-key operations. When a shorter route to a node is found, we simply push the new pair into the heap. The older pair becomes stale.

Why is this acceptable? Because when we pop a pair (d, node), we check whether d == dist[node]. If not, we know that a better path was discovered later, so the popped pair is obsolete. We ignore it.

This pattern is both simpler and often faster in practice than trying to update heap keys in place. It avoids complex heap manipulation and keeps the implementation clean.

What a naive programmer may ask: “But won’t the heap fill with duplicates?” Yes, it may contain multiple entries per node, but each edge relaxation causes at most one successful improvement per better path found. The asymptotic complexity remains efficient enough for standard constraints.

Step 8 — Why a Normal Queue Fails

A normal queue processes nodes in FIFO order, not by smallest cost. That works only when all edges have equal weight, which is exactly the unweighted BFS case. In weighted graphs, FIFO can process an expensive route before a cheaper one simply because it was discovered earlier.

For example:

0 -> 1 (100)
0 -> 2 (1)
2 -> 1 (1)

If you used a plain queue and locked node 1 when first discovered, you would record cost 100 and miss the real answer 2 through 0 → 2 → 1. The priority queue fixes this by always giving priority to the smallest tentative distance, not the earliest discovered node.

Step 9 — Why Negative Edges Break Dijkstra

Suppose you have:

0 -> 1 (2)
0 -> 2 (5)
2 -> 1 (-10)

The algorithm might finalize node 1 at cost 2 before seeing the route 0 → 2 → 1 with total cost -5. That means the “finalized” distance was not actually final. The invariant collapses.

That is why Dijkstra requires all edge weights to be non-negative. This is not a minor technical assumption; it is the reason the greedy proof works at all.

Step 10 — Clean C++17 Implementation

Method-only version, ready for interview use:

vector dijkstra(int n, vector>>& adj, int src) {
    const long long INF = 4'000'000'000'000'000'000LL;
    vector dist(n, INF);

    priority_queue,
                   vector>,
                   greater>> pq;

    dist[src] = 0;
    pq.push({0, src});

    while (!pq.empty()) {
        auto [d, node] = pq.top();
        pq.pop();

        if (d != dist[node]) continue;

        for (auto [next, w] : adj[node]) {
            long long nd = d + w;
            if (nd < dist[next]) {
                dist[next] = nd;
                pq.push({nd, next});
            }
        }
    }

    return dist;
}

What each line is really doing:

dist[src] = 0 means the cost of reaching the source from itself is zero. That is the starting truth from which everything else expands.

pq.push({0, src}) seeds the frontier with the source node. Nothing else is known yet.

auto [d, node] = pq.top() removes the current cheapest candidate. This is the most important operation in the entire algorithm.

if (d != dist[node]) continue; discards stale entries. This is the guard that keeps the implementation correct without manual heap updates.

Relaxation checks whether going through the current node gives a better route to a neighbor. This is the only way distances improve in Dijkstra.

Step 11 — A Very Fine-Grained Look at Relaxation

Relaxation is the local improvement step. For an edge u → v with weight w, we ask:

Is dist[u] + w better than dist[v]?

If yes, we update dist[v]. That is all relaxation is. But conceptually, it means: “I found a cheaper way to reach v by passing through u.”

This matters because Dijkstra does not guess the full shortest path upfront. It builds it gradually by repeated local improvements. Each time a node is finalized, its outgoing edges try to improve the neighbors. The algorithm is therefore a chain of tiny certainties leading to a global shortest-path answer.

Step 12 — Why This Greedy Choice Is Safe

The greedy choice is safe because the heap gives us the smallest tentative distance among all not-yet-finalized nodes. Since edge weights are non-negative, taking any extra edge can only keep the cost the same or increase it. So if node u is already the cheapest candidate, there is no hidden path through a more expensive node that can suddenly beat it.

That is the essence of the correctness proof:

Smallest tentative distance first + non-negative edges = final shortest distance when popped.

That one sentence is the full philosophy of Dijkstra.

Step 13 — Time and Space Complexity

Time Complexity: The standard complexity is O((V + E) log V). Each heap push and pop costs log V. We may relax each edge once for each improvement opportunity, and each successful improvement can generate a heap insertion. In practice, people often say O(E log V) because edge relaxations dominate.

Space Complexity: O(V + E). The adjacency list stores all edges, the distance array stores one distance per node, and the heap stores pending candidate states. The overall memory use remains linear in the size of the graph.

Step 14 — Final Intuition Summary

Dijkstra’s algorithm is a disciplined way of saying: “Always expand the cheapest path we currently know, and let cheaper discoveries overwrite older expensive ones.”

The heap is the engine. The distance array is the memory. The relaxation step is the improvement mechanism. The stale-entry check is the cleanup. The non-negative weight condition is the guarantee that makes the greedy step safe.

If you understand why the first popped valid distance for a node is final, you understand Dijkstra. Everything else is just implementation detail.
