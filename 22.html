LeetCode 22 — Generate Parentheses

Step 1 — Problem Statement

Input: An integer n, representing the number of pairs of parentheses.
Output: All possible strings of length 2n that form valid, well-formed parentheses combinations.
Key Constraints: The total number of answers can grow quickly, so the solution must avoid generating invalid strings unnecessarily. The problem is fundamentally about building only valid sequences, not filtering after the fact.
Edge Cases: The smallest meaningful input is n = 1. If you think beyond the usual constraints, n = 0 would naturally correspond to one empty string. Another important edge case is the maximum allowed n, where brute force becomes far too expensive. The tricky part is not correctness of a single string, but correctness of the entire generated set without duplicates.

Step 2 — Problem Understanding & Approach Overview

This problem is really asking: how do we construct every valid parentheses string of length 2n without ever building invalid ones? The core challenge is combinatorial generation under a prefix-validity constraint. This is a classic backtracking / DFS generation problem. The instinctive mental model is: at every position, you may place either '(' or ')', but only if doing so keeps the partial string “safe.” The subtle trap is to generate all 22n strings and validate them later; that wastes enormous work. Another common mistake is allowing more closing brackets than opening brackets at some prefix, which immediately breaks validity.

Step 3 — Brute Force Solution

The naive idea is to generate every string of length 2n using parentheses choices, then check whether each string is valid. For each generated string, we scan left to right and maintain a balance counter: an opening parenthesis increases balance, a closing parenthesis decreases it. A string is valid only if balance never becomes negative and ends at zero. 

Brute Force Pseudocode

generate every string s of length 2n using '(' and ')'
for each generated string s:
    if s is valid:
        add s to answer

isValid(s):
    balance = 0
    for each character c in s:
        if c == '(':
            balance++
        else:
            balance--
        if balance < 0:
            return false
    return balance == 0

Time Complexity: O(22n × n). There are 22n candidate strings, and each validation takes O(n).
Space Complexity: O(n) for recursion / temporary string storage, ignoring the output.
Bottleneck: The bottleneck is exploring huge numbers of invalid strings that should never have been built in the first place.

Step 4 — Intuition Building

Test Case 1

Input: n = 1
Current state: We need one '(' and one ')'. There is only one valid answer.
Action: Start with '(' because a valid string cannot begin with ')'. Then place ')'.
Result: "()"

This tiny case already reveals the key rule: a closing bracket is only legal if there is an unmatched opening bracket before it.

Test Case 2

Input: n = 2
Current state: We need two opens and two closes.
Action: Build only prefixes that never become invalid:
  Prefix "(" can still grow into valid strings.
  Prefix ")" is invalid immediately, so it must never be explored.
  From "((", we can close once to get "(()", then close again to get "(())".
  From "()", we can open again to get "()(", then close to get "()()".
Result: "(())", "()()"

The important discovery is that we are not generating strings blindly. We are growing a tree of prefixes, and pruning immediately when a prefix cannot possibly lead to a valid answer.

Test Case 3

Input: n = 3
Current state: We need three opens and three closes. A prefix is valid only if:
  openCount ≤ n
  closeCount ≤ openCount
Action: Explore valid branches only:
  "(((" is allowed because we still have opens left.
  "((()" is allowed because closeCount never exceeds openCount.
  "((())" is still safe.
  "((()))" becomes a complete answer.
  Other branches like "())" are cut off the moment a close appears too early.
Result: All valid combinations are produced without duplicate checking and without post-validation.

What inefficiency disappears? The entire universe of invalid sequences is never constructed. That is the real optimization.
What should trigger this same approach in future problems? Whenever you are asked to generate all strings/combinations/permutations under a prefix rule, think backtracking with pruning.

Step 5 — Optimized Solution

This problem has one meaningful optimal solution: backtracking with two counters. There is no separate intermediate optimization level worth isolating here, because the key leap is already to stop generating invalid prefixes. The fully optimal approach builds only valid partial strings.

The two counters are:
openCount — how many '(' have been used so far.
closeCount — how many ')' have been used so far.

The rules are simple:
1. We may add '(' if openCount < n.
2. We may add ')' if closeCount < openCount.
3. A string is complete when its length becomes 2n.

Why this works:
Any valid parentheses string must satisfy the prefix condition: at no point can the number of closing brackets exceed the number of opening brackets. These two counters enforce that invariant directly during construction. 

C++17 Code

vector<string> generateParenthesis(int n) {
    vector<string> ans;
    string current;

    function<void(int, int)> dfs = [&](int openCount, int closeCount) {
        if ((int)current.size() == 2 * n) {
            ans.push_back(current);
            return;
        }

        if (openCount < n) {
            current.push_back('(');
            dfs(openCount + 1, closeCount);
            current.pop_back();
        }

        if (closeCount < openCount) {
            current.push_back(')');
            dfs(openCount, closeCount + 1);
            current.pop_back();
        }
    };

    dfs(0, 0);
    return ans;
}

Dry Run — n = 3

Start
Current: ""
openCount = 0, closeCount = 0

Step 1 — Add '('
Current: "("
openCount = 1, closeCount = 0
Reason: we still have opens left.

Step 2 — Add '(' again
Current: "(("
openCount = 2, closeCount = 0

Step 3 — Add '(' again
Current: "((("
openCount = 3, closeCount = 0
Now no more '(' can be added.

Step 4 — Add ')'
Current: "((()"
openCount = 3, closeCount = 1

Step 5 — Add ')'
Current: "((())"
openCount = 3, closeCount = 2

Step 6 — Add ')' to complete
Current: "((()))"
openCount = 3, closeCount = 3
Length = 6 = 2n, so this is a valid answer.

The backtracking then returns and explores the next valid branch:
Current: "(()"
It eventually produces "()()", "(())()", "()(())", "()()()", and the full set of valid combinations.

Extreme Edge Case Handling: For the smallest case n = 1, the same rules still work: we add '(' once, then ')' once, and stop exactly when the length reaches 2. There is no special-case code needed.
If you consider n = 0 conceptually, the empty string would be the only valid output; the same recursion pattern could handle that too if allowed by the problem definition.

Time Complexity: The number of valid sequences is the nth Catalan number, which is much smaller than 22n. A standard bound is O(Cn), and each sequence has length 2n, so the total work is O(Cn × n).
Space Complexity: O(n) recursion depth and O(n) temporary string storage, excluding the output list.
Algorithm Name: Backtracking / DFS with pruning.

Final Interview Intuition

The central insight is not “generate parentheses.” It is:
build only prefixes that can still become valid, and enforce validity while constructing the string.

The moment you see a problem that asks for all valid arrangements with a local rule that depends on the prefix, think of backtracking with pruning.
