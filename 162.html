LeetCode 162 — Find Peak Element
Step 1 — Problem Statement

Input: An integer array nums. A peak element is an index i such that nums[i] > nums[i - 1] and nums[i] > nums[i + 1], where the virtual elements outside the array are treated as -∞. The array is guaranteed to have at least one peak.

Output: Return any peak index.

Key Constraints: The array has at least one element. Adjacent elements are not equal in the classic problem setting, which is important because it lets us reason about a strict rising or falling slope. The answer does not need to be the leftmost or rightmost peak; any valid peak is acceptable.

Edge Cases: A single-element array, a strictly increasing array, a strictly decreasing array, multiple peaks, and peaks near the boundaries. The boundary rule with virtual -∞ matters: the first or last element can be a peak.

Step 2 — Problem Understanding & Approach Overview

Strip away the story: this is really asking for a local maximum in an array where you are allowed to return any one of them. The core challenge is to do better than scanning every element one by one.

This is a binary search on structure problem. The mental model is not “find the biggest number”; it is “find a place where the slope changes from rising to falling.” If the middle is rising to the right, then a peak must exist on the right side. If the middle is falling to the right, then a peak must exist on the left side including the middle.

The subtle trap is to check both neighbors for every index and stop at the first peak. That works, but it wastes the structure of the array and costs O(n). Another common mistake is to move the binary search boundary incorrectly by using mid - 1 or mid + 1 without preserving the guarantee that a peak still exists in the remaining range.

Step 3 — Brute Force Solution

The naive idea is simple: inspect every index and test whether it is greater than its left and right neighbors. For boundary indices, use the virtual -∞ values. 

Pseudocode:

for i from 0 to n - 1:
    left  = (i == 0) ? -∞ : nums[i - 1]
    right = (i == n - 1) ? -∞ : nums[i + 1]

    if nums[i] > left and nums[i] > right:
        return i

Time Complexity: O(n) — in the worst case, we may check every element before finding a peak.

Space Complexity: O(1) — only a constant amount of extra memory is used.

Performance Bottleneck: The bottleneck is the full linear scan. We are using no information from the shape of the array to skip work.

Step 4 — Intuition Building

Test Case 1

Input: 1

    Single element
    Left neighbor = -∞, Right neighbor = -∞
Action: Check the only index
Result: index 0 is a peak

Test Case 2

Input: 1 2 3 1

    The array rises and then falls
    Peak is at the turning point
Action: Scan from left
    1 is not a peak
    2 is not a peak
    3 is greater than 2 and 1
Result: index 2 is a peak

Test Case 3

Input: 1 2 1 3 5 6 4

    There are multiple peaks
    Peaks exist at 2 and 6? No — index 2 is not a peak because 1 is lower, but 2 is a peak at index 1; 6 is a peak at index 5
    The exact answer does not matter; any valid peak is accepted
Action: Instead of checking all indices, observe slope
    If mid is rising toward mid + 1, a peak must exist on the right side
    If mid is falling toward mid + 1, a peak must exist on the left side
Result: The search can discard half the range each step

This is the key discovery: a peak is guaranteed to exist in whichever side still contains a slope change. That means we can use binary search even though the array is not fully sorted.

An extreme edge case that often scares candidates is a strictly increasing array such as 1 2 3 4. The optimal logic still works because the last element is a peak due to the virtual -∞ on the right. Likewise, a strictly decreasing array returns the first element.

The signal that should immediately make you think of this approach is: “find any local extremum, and the neighborhood comparison tells you which half still must contain one.”

Step 5 — Optimized Solution

There is one fully optimal idea here: binary search on the slope. At each step, compare nums[mid] with nums[mid + 1]. If the slope is rising, a peak must exist to the right. If the slope is falling, a peak must exist to the left, possibly at mid itself.

Algorithm Name: Binary Search on Slope

Pseudocode:

l = 0
r = n - 1

while l < r:
    mid = l + (r - l) / 2

    if nums[mid] < nums[mid + 1]:
        l = mid + 1
    else:
        r = mid

return l

Why this works: If nums[mid] < nums[mid + 1], we are on an ascending slope, so the right half must contain a peak. If nums[mid] > nums[mid + 1], we are on a descending slope, so a peak exists on the left half including mid. We never discard all peaks. 

C++17 Code:

int findPeakElement(vector& nums) {
    int l = 0, r = (int)nums.size() - 1;

    while (l < r) {
        int mid = l + (r - l) / 2;

        if (nums[mid] < nums[mid + 1]) {
            l = mid + 1;
        } else {
            r = mid;
        }
    }

    return l;
}

Dry Run:

Input: 1 2 1 3 5 6 4

Step 1
    l = 0, r = 6
    mid = 3
    nums[mid] = 3, nums[mid + 1] = 5
    Rising slope → peak must be on the right
Action: l = mid + 1 = 4

Step 2
    l = 4, r = 6
    mid = 5
    nums[mid] = 6, nums[mid + 1] = 4
    Falling slope → peak must be on the left half including mid
Action: r = mid = 5

Step 3
    l = 4, r = 5
    mid = 4
    nums[mid] = 5, nums[mid + 1] = 6
    Rising slope → peak must be on the right
Action: l = mid + 1 = 5

End
    l = r = 5
Result: index 5, value 6, is a peak

Extreme Edge Case: For a single-element array [7], the loop never runs because l == r immediately, and we correctly return index 0.

Time Complexity: O(log n) — each iteration discards half the search space.

Space Complexity: O(1) — only a few variables are used.
