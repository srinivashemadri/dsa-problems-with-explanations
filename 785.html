LeetCode 785 — Is Graph Bipartite?

1. Problem Statement

Input: An undirected graph given as an adjacency list, where graph[i] contains all neighbors of node i. The nodes are labeled from 0 to n - 1.

Output: Return true if the graph can be divided into two sets such that every edge connects a node from one set to a node in the other set. Otherwise return false.

Key Constraints: This is an undirected graph, and it may be disconnected. That matters a lot, because checking only one component is not enough. The graph is really asking for a valid two-coloring: every edge must connect opposite colors.

Edge Cases: An empty graph is trivially bipartite. A graph with one isolated node is bipartite. A disconnected graph may have some bipartite components and one bad component that makes the whole answer false. A self-loop, if present, immediately breaks bipartiteness because a node would need to be in both partitions at once. Odd cycles such as triangles are the classic failure case. Duplicate edges do not change the answer; they only repeat the same check.

2. Problem Understanding & Approach Overview

Strip away the graph story, and this is really a consistency problem: can we assign one of two labels to every node so that every edge always goes across labels, never inside the same label?

The core challenge is detecting whether the graph contains an odd cycle. That is the exact obstruction to a valid two-coloring.

This is a graph coloring / bipartite check problem. The mental model is simple: start coloring a node red, force all its neighbors blue, force their neighbors red, and keep propagating. The moment two adjacent nodes demand the same color, the graph is impossible.

The subtle trap most candidates hit is starting from node 0 only and forgetting disconnected components. Another common mistake is using “visited” without remembering the actual color; for this problem, the color itself is the state.

3. Brute Force Solution

The naive idea is to try every possible partition of the nodes into two sets and check whether every edge goes across the partition. 

for every assignment of n nodes into two groups:
    for every edge (u, v):
        if u and v are in the same group:
            this assignment fails
    if no edge failed:
        return true

return false

Why this is slow: There are 2^n possible assignments, and each one requires checking the edges. If the graph has E edges, the time complexity is O(2^n × E). The bottleneck is obvious: you are enumerating all possible colorings.

Space Complexity: O(1) extra space if you generate assignments implicitly, or more if you store them. Either way, time is the real killer.

4. Intuition Building

Test Case 1

Input: graph = [[], [ ], [ ]]

Current state: three isolated nodes, no edges at all.

Action: Each node can stay uncolored or be colored independently, because no edge ever forces a conflict.

Result: true

This is a useful reminder that edges, not nodes, create constraints. An isolated node never causes trouble.

Test Case 2

Input: graph = [[1], [0,2], [1,3], [2]]

Start at node 0 → color 0 as Red. Node 1 must be Blue. Node 2 must be Red. Node 3 must be Blue.

Action: Every edge keeps forcing the opposite color, and no contradiction appears.

Result: true

This is the pattern the optimized algorithm exploits: once a node is colored, all its neighbors are forced. There is no freedom left after that.

Test Case 3 (Edge Case)

Input: graph = [[1,2], [0,2], [0,1]]

Start at node 0 → color 0 as Red. Node 1 becomes Blue. Node 2 also becomes Blue because it is adjacent to 0.

Action: Now look at edge (1,2). Both endpoints are Blue, so the constraint is broken.

Result: false

This is the classic odd-cycle failure. A triangle cannot be split into two groups without putting one edge inside a group.

The key insight is that you do not need to search all partitions. The graph itself tells you the partition by propagation. Every edge forces the opposite color, so a BFS/DFS coloring pass is enough.

The signal that should immediately make you think of this approach is: “split the graph into two groups”, “no two adjacent nodes should share a group”, or any wording that sounds like a two-color consistency check.

5. Optimized Solution

The fully optimal and standard approach is BFS/DFS two-coloring. I’ll use BFS here because it makes the propagation and conflict detection very explicit. 

bool isBipartite(vector<vector<int>>& graph) {
    int n = graph.size();
    vector<int> color(n, -1);   // -1 = uncolored, 0 and 1 are the two groups
    queue<int> q;

    for (int start = 0; start < n; ++start) {
        if (color[start] != -1) continue;

        color[start] = 0;
        q.push(start);

        while (!q.empty()) {
            int node = q.front();
            q.pop();

            for (int nei : graph[node]) {
                if (color[nei] == -1) {
                    color[nei] = 1 - color[node];
                    q.push(nei);
                } else if (color[nei] == color[node]) {
                    return false;
                }
            }
        }
    }

    return true;
}

Why this works: The moment you color a node, all of its neighbors are forced to take the opposite color. If any neighbor already has the same color, the graph contains an odd cycle or an equivalent contradiction. If every component finishes without conflict, then a valid two-coloring exists.

Why color uses -1: That single array plays two roles at once. It marks whether a node has been processed, and it stores the actual partition assignment. That is cleaner than maintaining a separate visited array.

Why we loop over every node: Because the graph may be disconnected. A valid component does not prove the whole graph is valid. Every uncolored node must become a new BFS root.

Dry Run

Example: graph = [[1,3], [0,2], [1,3], [0,2]]

Step 1 — Start at node 0

color[0] = 0
queue = [0]

Step 2 — Process node 0

Neighbors: 1, 3
color[1] = 1
color[3] = 1
queue = [1, 3]

Step 3 — Process node 1

Neighbor: 0 already colored 0, valid
Neighbor: 2 uncolored → color[2] = 0
queue = [3, 2]

Step 4 — Process node 3

Neighbor: 0 already colored 0, valid
Neighbor: 2 already colored 0, valid

Step 5 — Process node 2

Neighbor: 1 already colored 1, valid
Neighbor: 3 already colored 1, valid

Final Result: No conflict appeared, so return true.

How the extreme edge case is handled

Suppose a node has itself in its adjacency list. When BFS reaches that edge, the neighbor is the same node and therefore has the same color. The code instantly returns false. That is exactly the correct behavior.

Another subtle case is a disconnected graph like [[1], [0], [3], [2]]. The first component may succeed, but the outer loop still starts BFS from the next uncolored node, so the second component is checked too. That is why the outer loop is not optional.

Time Complexity: O(V + E), where V is the number of nodes and E is the number of edges. Every node is colored at most once, and every adjacency entry is inspected at most once. Because the graph is undirected and represented as adjacency lists, each edge may be seen twice overall, which is still linear.

Space Complexity: O(V) for the color array and the BFS queue in the worst case. No extra structure proportional to the number of edges is needed.

Name of the algorithm: Two-coloring using BFS, also known as bipartite graph checking by graph coloring.
