LeetCode 1 — Two Sum

1. Problem Statement

Input: An integer array nums and an integer target.

Output: Return the indices of the two distinct elements whose sum equals target.

Key Constraints: You cannot use the same element twice. The problem guarantees exactly one valid answer, so you do not need to handle “no solution” as a normal case in the final LeetCode setting. The output must be the indices, not the values.

Edge Cases: empty array, single element array, duplicate values, negative numbers, target formed by equal numbers such as 3 + 3, and the case where the correct pair appears only after several earlier elements have already been seen.

2. Problem Understanding & Approach Overview

This problem is really asking: for every number, can we instantly know whether its complement target - nums[i] has already appeared?

The core challenge is fast pair lookup. Without extra structure, you are forced into repeated scanning. This is a classic pair lookup / complement search problem.

The mental model is simple: walk through the array once while remembering what you have seen so far. At each position, ask whether the missing half of the sum is already in memory.

The subtle trap is inserting the current element into the map before checking the complement. That can accidentally let the same index match itself when target = 2 * nums[i].

3. Brute Force Solution

The naive idea is to check every pair of indices.

for i from 0 to n-1:
    for j from i+1 to n-1:
        if nums[i] + nums[j] == target:
            return [i, j]

Why it works: it explicitly tests every possible pair, so it cannot miss the answer.

Time Complexity: O(n²). There are two nested loops, and the inner loop may run almost n times for each i.

Space Complexity: O(1). No extra data structure is required beyond a few variables.

Bottleneck: the repeated re-checking of pairs. The same numbers are compared many times.

4. Intuition Building
Test Case 1

Input: 2 7 11 15, target = 9

Current state: nothing seen yet.

Action: Read 2. Complement needed is 7. It is not in memory, so store 2.

Action: Read 7. Complement needed is 2. It is already stored.

Result: Return indices of 2 and 7.

This shows the key idea: instead of comparing every pair, we compare the current number against a memory of past numbers.

Test Case 2

Input: 3 2 4, target = 6

Current state: start with an empty map.

Action: Read 3. Complement needed is 3. Not found, so store 3 → index 0.

Action: Read 2. Complement needed is 4. Not found, so store 2 → index 1.

Action: Read 4. Complement needed is 2. Found at index 1.

Result: Return indices 1 and 2.

The pattern becomes clearer: the answer is found the first time the complement appears among previously seen values. This is why a hash map removes the need for the inner loop.

Test Case 3 (Edge Case)

Input: 3 3, target = 6

Current state: empty map.

Action: Read first 3. Complement needed is also 3. Not found yet, so store 3 → index 0.

Action: Read second 3. Complement needed is 3. Found at index 0.

Result: Return indices 0 and 1.

This is the rare case that exposes a common bug. If you store the current value first and then search, the algorithm may incorrectly reuse the same element. The correct order is: search first, then store.

Immediate signal for this approach in a future problem: whenever you see “find two numbers that add up to a target” and the output depends on indices or positions, think of a hash map of complements.

5. Optimized Solution

Algorithm Name: One-pass Hash Map / Complement Lookup.

The further insight is that you do not need to wait until the end to compare everything. The moment you read a value, you can determine whether its complement has already appeared. That gives a true single-pass solution.

For each index i from 0 to n-1:
    needed = target - nums[i]
    if needed exists in map:
        return [map[needed], i]
    store nums[i] with index i in map

Why this is optimal: every element is processed once, and each lookup/insert is expected O(1) with a hash table.

Time Complexity: O(n). Each element is handled once, and each hash map operation is expected constant time.

Space Complexity: O(n). In the worst case, all numbers may need to be stored before the answer is found.

Dry Run:

Input: nums = [2, 7, 11, 15], target = 9

Pivot idea: not applicable here; we are doing complement search.

Step 1
Current number: 2
Needed: 7
Map before lookup: {}
7 not found
Store: 2 -> 0
Map after store: {2: 0}

Step 2
Current number: 7
Needed: 2
Map before lookup: {2: 0}
2 found at index 0
Final answer: [0, 1]

Edge case handling: for input like [3, 3] with target 6, the first 3 is stored, and the second 3 correctly matches it. Because lookup happens before insertion, the same index is never reused.

Interview-ready C++17 code:

vector<int> twoSum(vector<int>& nums, int target) {
    unordered_map<int, int> mp;

    for (int i = 0; i < (int)nums.size(); i++) {
        int need = target - nums[i];

        auto it = mp.find(need);
        if (it != mp.end()) {
            return {it->second, i};
        }

        mp[nums[i]] = i;
    }

    return {};
}

This solution is the standard optimal approach for LeetCode 1 because it reduces pair search from quadratic scanning to constant-time complement checks.
