LeetCode 787 — Explanation of the Given Code

1. What this code is doing

The code tries to find the cheapest price from src to dst with at most k stops. It builds a graph from the flight list, then uses a queue to explore possible routes while keeping track of both the current cost and the number of flights used so far.

2. The code

class Solution { public: int findCheapestPrice(int n, vector<vector<int>>& flights, int src, int dst, int k) { queue<tuple<int, int, int>> q; vector<vector<pair<int, int>>> adj(n); for(int i=0;i<flights.size();i++){ int from = flights[i][0]; int to = flights[i][1]; int we = flights[i][2]; adj[from].push_back({to, we}); } vector<int> dist(n, INT_MAX); dist[src] = 0; q.push(make_tuple(0, src, 0)); while(!q.empty()){ int stops = get<0>(q.front()); int curr = get<1>(q.front()); int distance = get<2>(q.front()); q.pop(); if(stops > k ) continue; if(curr == dst) continue; for(int i=0;i<adj[curr].size();i++){ int nxt = adj[curr][i].first; int we = adj[curr][i].second; if(dist[nxt] > distance + we){ q.push({stops+1, nxt, distance + we}); dist[nxt] = distance + we; } } } return dist[dst] == INT_MAX ? -1: dist[dst]; } };

3. Line-by-line explanation

queue<tuple<int, int, int>> q;
This queue stores states of the form (stops, city, cost). It is the main work queue for exploring paths.
vector<vector<pair<int, int>>> adj(n);
This creates an adjacency list. For every city, it stores all outgoing flights as (next_city, price).
for(...) ... adj[from].push_back({to, we});
This converts the given flight list into graph form, so later the code can directly visit all neighbors of a city.
vector<int> dist(n, INT_MAX);
dist[i] stores the cheapest cost found so far to reach city i.
dist[src] = 0;
The starting city has cost zero.
q.push(make_tuple(0, src, 0));
The first state means: 0 stops used, currently at src, total cost 0.
while(!q.empty())
Keep processing states until there is nothing left to explore.
stops = get<0>(...), curr = get<1>(...), distance = get<2>(...)
Read the current state from the queue.
if(stops > k) continue;
If this path already used too many stops, ignore it.
if(curr == dst) continue;
If the destination is already reached, the code does not expand this path further.
for each neighbor of curr
Try all outgoing flights from the current city.
if(dist[nxt] > distance + we)
Only push the next city if the new route is cheaper than the best one recorded so far for that city.
q.push({stops+1, nxt, distance + we});
Add the new state to the queue.
dist[nxt] = distance + we;
Save the cheaper cost for that city.
return dist[dst] == INT_MAX ? -1 : dist[dst];
If the destination was never reached, return -1; otherwise return the cheapest cost found.

4. Intuition behind the code

The code is trying to do two things at once:

First, it explores routes from the source to all reachable cities. Second, it tries to avoid wasting work by remembering the cheapest cost found so far for each city.

The queue stores full path states, because the same city can be reached with different costs and different numbers of stops. The stop limit is important because a route may be cheap but still invalid if it uses too many stops.

So the mental model is: "expand only useful routes, and throw away routes that are already too expensive or too long."

5. Important subtle point

This implementation uses a single dist[node] array. That is a pruning idea, but for this problem it is not always fully correct in all cases, because the cheapest way to reach a city is not always the best way to reach the destination within the stop limit.

Example idea: a path that reaches an intermediate city with a slightly higher cost but fewer stops can still lead to the final answer, while a cheaper path with more stops may block that route if the stop limit is tight.

So the core idea is right, but the pruning strategy is the part that can break correctness in edge cases.

6. What each variable means

adj → graph of flights

dist → cheapest known cost to each city

q → states waiting to be processed

stops → number of flights already taken

curr → current city

distance → total cost from source to current city

7. Tiny dry run

Suppose the flights are:

0 -> 1 cost 100 1 -> 2 cost 100 0 -> 2 cost 500

Start with (0, 0, 0).

From city 0, the code can go to city 1 with cost 100 and city 2 with cost 500.

It stores the cheaper known costs in dist, pushes the new states into the queue, and continues until every useful route is checked.

The final answer becomes the cheapest valid route within the stop limit.

8. Final takeaway

This code is a graph traversal with state. The extra state is not just the city, but also the number of stops and the total cost. That is the real reason the problem is harder than plain shortest path.

The idea is good, but for full correctness the stop dimension usually needs stronger tracking than a single dist[node] array.
