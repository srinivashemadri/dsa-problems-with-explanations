LeetCode 1631 — Path With Minimum Effort
Step 1 — Problem Statement

Input: You are given a grid heights of size m × n. You start at the top-left cell (0, 0) and want to reach the bottom-right cell (m - 1, n - 1). From any cell, you may move up, down, left, or right.

Output: Return the minimum possible effort required for a path from start to end. The effort of a path is not the sum of all moves; it is the maximum absolute difference between heights of adjacent cells along that path.

Key Constraints: The grid is small enough for graph algorithms on an implicit graph, but large enough that brute-force path enumeration is impossible. Heights can be large, so the absolute differences can also be large. The real structure is a weighted graph with at most m × n nodes and at most about 4mn edges.

Edge Cases: A 1 × 1 grid has no move at all, so the answer is 0. A single row or single column has exactly one path. If all heights are identical, every edge has cost 0, so the answer is 0. If there is one very steep cell among otherwise flat terrain, the optimal route may detour around it. If multiple paths have the same minimum effort, any of them is valid, but the returned value must still be that minimum. Large height values matter because the difference can be big, so use a type safe for differences.

Step 2 — Problem Understanding & Approach Overview

Strip away the grid story and this becomes: find a path from source to destination whose worst edge is as small as possible. This is a classic minimax path problem on a weighted graph.

The core challenge is that the path score is not additive. When you extend a path by one edge, the new score becomes the maximum of the old score and the new edge weight. That makes ordinary shortest-path intuition tricky at first.

Category: Graph, shortest path on an implicit grid, minimax optimization, Dijkstra-style reasoning.

Mental Model: Imagine every move has a “pain” equal to the height difference. A path is good if its worst pain is small. You are not trying to minimize total pain; you are trying to minimize the most painful step.

Subtle Trap: Many candidates try plain BFS because movement is on a grid, or they try ordinary Dijkstra by summing edge weights. Both are wrong for the objective. The correct state is the minimum possible bottleneck to each cell, not a distance sum.

Step 3 — Brute Force Solution

The most naive way is to enumerate every possible simple path from start to end, compute the maximum edge difference on that path, and take the minimum among all paths. 

DFS(r, c, currentMax):
    if (r, c) is destination:
        update global answer with currentMax
        return

    mark (r, c) as visited

    for each valid neighbor (nr, nc):
        if not visited[nr][nc]:
            edgeCost = abs(heights[r][c] - heights[nr][nc])
            nextMax = max(currentMax, edgeCost)
            DFS(nr, nc, nextMax)

    unmark (r, c)

This is correct because it checks every possible route, but it is completely impractical. The performance bottleneck is the number of paths, which grows exponentially. In a grid, the number of simple paths can explode extremely fast, so even moderate input sizes become impossible.

Time Complexity: Exponential in the number of cells. A rough upper bound is often described as O(4mn) in spirit, though the exact count depends on path constraints. The key point is that it is exponential and unusable.

Space Complexity: O(mn) for recursion stack and visited tracking.

This is the key discovery: the score of a path is controlled by its worst edge. That means we do not care about accumulating cost the way ordinary shortest path does. We care about whether a route can keep every step under a threshold, or how small that threshold can be.

A very useful signal in future problems is this: “minimize the maximum edge/step/fee/effort on a path.” That almost always points to a minimax graph pattern, often solved by Dijkstra on a modified cost, or by binary search on the answer plus feasibility checking.

Step 5 — Optimized Solution

There are two meaningful optimization levels here. The first one turns the problem into a feasibility question and uses binary search. The second one is the fully optimal and most elegant graph solution: Dijkstra on a bottleneck cost.

Optimized Solution 1 — Binary Search on Answer + BFS/DFS Feasibility

The insight is: if we guess an effort limit X, we can check whether there exists a path from start to end using only edges whose height difference is at most X. This check is monotonic: if a path exists for X, then it also exists for any larger value. That monotonicity makes binary search valid. 

low = 0
high = maximum absolute difference between any adjacent cells

while low < high:
    mid = (low + high) / 2
    if destination reachable using only edges with diff <= mid:
        high = mid
    else:
        low = mid + 1

return low

Time Complexity: Each feasibility check is O(mn). Binary search runs for O(log D) steps, where D is the maximum possible edge difference. So total complexity is O(mn log D).

Space Complexity: O(mn) for visited/state during BFS or DFS.

What Was Eliminated Compared to Brute Force: We no longer enumerate paths. Instead, we only ask whether a threshold is sufficient, which collapses an exponential search space into a polynomial number of grid traversals.

Optimized Solution 2 — Dijkstra on a Minimax Cost Function

This is the best-known direct solution. Treat each cell as a graph node, and the edge weight between adjacent cells as the absolute height difference. The cost of a path is not the sum of edge weights; it is the maximum edge weight seen so far.

The Dijkstra idea still works because when you extend a path, the new path cost is max(currentEffort, edgeCost), which never decreases. That monotonic behavior is exactly what Dijkstra needs for label-setting.

C++17 Code: 

int minimumEffortPath(vector<vector<int>>& heights) {
    int m = heights.size();
    int n = heights[0].size();

    vector<vector<int>> dist(m, vector<int>(n, INT_MAX));
    using State = pair<int, pair<int, int>>; // {effort, {r, c}}
    priority_queue<State, vector<State>, greater<State>> pq;

    dist[0][0] = 0;
    pq.push({0, {0, 0}});

    int dr[4] = {1, -1, 0, 0};
    int dc[4] = {0, 0, 1, -1};

    while (!pq.empty()) {
        auto [effort, cell] = pq.top();
        pq.pop();

        int r = cell.first;
        int c = cell.second;

        if (effort != dist[r][c]) continue;
        if (r == m - 1 && c == n - 1) return effort;

        for (int k = 0; k < 4; k++) {
            int nr = r + dr[k];
            int nc = c + dc[k];

            if (nr < 0 || nc < 0 || nr >= m || nc >= n) continue;

            int edgeCost = abs(heights[r][c] - heights[nr][nc]);
            int nextEffort = max(effort, edgeCost);

            if (nextEffort < dist[nr][nc]) {
                dist[nr][nc] = nextEffort;
                pq.push({nextEffort, {nr, nc}});
            }
        }
    }

    return 0;
}

Why the data structure works: The priority queue always expands the cell with the smallest known bottleneck effort first. If a cell is popped with effort e, then there is no better path to that cell that can appear later, because any later path would have effort at least e. This is the same core invariant as Dijkstra, but with a different relaxation rule.

    Neighbors:
    (1,2): edge = |2-2| = 0, nextEffort = max(1, 0) = 1

    Neighbors:
    (2,2): edge = |2-5| = 3, nextEffort = max(1, 3) = 3

    Neighbors:
    (2,1): edge = |2-3| = 1, nextEffort = max(1, 1) = 1

    Better than 3 through the earlier route

Edge Case Check — 1 × 1 Grid: The queue starts with the source, and the source is also the destination. We return 0 immediately. No special hacks are needed.

Time Complexity: The grid has V = mn vertices and E = O(mn) edges. Each relaxation may push into the heap, and each pop/push costs log(mn). So the total complexity is O(mn log(mn)).

Space Complexity: O(mn) for the distance table and the priority queue.

Name of the Algorithm: Dijkstra’s algorithm on a minimax / bottleneck path metric.

Final Interview Intuition

The one-line memory hook for this problem is: “Every path has a bottleneck; minimize the bottleneck.”

If you see a problem where the path score is defined by the maximum edge/step cost rather than the sum, think immediately about: binary search + reachability or Dijkstra with max-based relaxation.
