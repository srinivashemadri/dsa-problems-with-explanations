LeetCode 4 — Median of Two Sorted Arrays
Step 1 — Problem Statement

Input: Two sorted arrays, usually called nums1 and nums2, may have different lengths. Either array may be empty. The arrays are sorted in non-decreasing order, so duplicates are allowed.

Output: Return the median of the combined sorted sequence formed by all elements from both arrays.

Key Constraints: The arrays are already sorted, and the goal is not to fully merge them unless necessary. The strongest constraint that shapes the solution is that the answer must be found faster than linear time in the optimal approach, so the sorted property must be exploited directly.

Edge Cases: One array can be empty, the total number of elements can be odd or even, values can be negative, arrays can contain duplicates, and one array can be much smaller than the other. The boundary partitions themselves are also edge cases: sometimes the correct split uses zero elements from one array or all elements from it.

Step 2 — Problem Understanding & Approach Overview

This problem is really asking for the element in the middle of the merged sorted order, without actually paying the cost of fully merging unless we choose the brute-force route. In other words, it is a rank/partition problem disguised as a median problem.

The core algorithmic challenge is: find the correct split point between the two arrays so that every element on the left side is less than or equal to every element on the right side.

This belongs to the category of binary search on partition. The mental model is to imagine cutting both arrays into a left half and a right half, then adjusting the cut until the two halves are perfectly balanced.

The subtle trap is to think only in terms of merging arrays, or to binary search on values instead of partitions. Another common mistake is to binary search the larger array. The clean and safe version always binary searches the smaller array.

Step 3 — Brute Force Solution

The naive approach is to merge both sorted arrays into one sorted array, then read the median from the middle. 

Brute Force Pseudocode

1. Create a new array merged.
2. Use two pointers i and j starting at 0.
3. While both arrays still have elements:
      compare nums1[i] and nums2[j]
      append the smaller one to merged
      move the corresponding pointer
4. Append any remaining elements from nums1.
5. Append any remaining elements from nums2.
6. Let n = merged.size().
7. If n is odd:
      return merged[n / 2]
   Else:
      return (merged[n / 2 - 1] + merged[n / 2]) / 2.0

Time Complexity: O(m + n). Every element is processed once during the merge.

Space Complexity: O(m + n). The merged array stores all elements.

Bottleneck: The memory usage is unnecessary, because only the middle two elements of the merged order are actually needed.

Step 4 — Intuition Building

Test Case 1

Input: nums1 = [1, 3], nums2 = [2]
Observation: Merged order would be [1, 2, 3]. The median is the middle element, 2.
Action: If we fully merge, we directly see the answer. But this also shows the deeper pattern: the median depends only on the middle rank, not on the full merged list.
Result: 2

Test Case 2

Input: nums1 = [1, 2], nums2 = [3, 4]
Observation: Merged order would be [1, 2, 3, 4]. The median is the average of the two middle elements, 2 and 3.
Action: This tells us that for even total length, we need the maximum of the left half and the minimum of the right half.
Result: 2.5

Test Case 3 (Edge Case)

Input: nums1 = [], nums2 = [1]
Observation: One array is empty. A merge-based solution still works, but the optimal approach must also handle this cleanly without special-case code explosion.
Action: The partition view treats the empty side as having no left elements and no right elements, which is exactly where sentinel values become useful.
Result: 1

The inefficiency in the brute-force approach is now visible: we are computing far more of the merged order than we actually need. The structure to exploit is not “sort everything,” but “find the exact split where the left half contains the correct number of elements.”

The future signal that should immediately suggest the same approach is: “two sorted arrays” + “need median or k-th element” + “do not fully merge”.

Step 5 — Optimized Solution 1 (Intermediate)

The first optimization is simple but useful: instead of building the full merged array, keep only enough information to reach the median position. You still use two pointers, but you stop once you have walked past the middle. 

Optimized 1 Pseudocode

1. Use two pointers i and j.
2. Keep track of the last two seen values while simulating a merge.
3. Stop when the number of processed elements reaches the median position.
4. If total length is odd, return the current middle value.
5. If total length is even, return the average of the two middle values.

Time Complexity: O(m + n) in the worst case, because in the worst case you still advance through most of both arrays.

Space Complexity: O(1), because no merged array is stored.

What was eliminated: The extra O(m + n) storage from the brute-force approach.

Step 5 — Optimized Solution 2 (Best Known / Fully Optimal)

The fully optimal idea is to binary search the partition point in the smaller array. We choose how many elements of the smaller array go to the left half, and the rest of the left half comes from the larger array.

Let the smaller array be A with length m, and the larger array be B with length n. We want:

left side size = (m + n + 1) / 2

The +1 is crucial. For odd total length, it makes the left side contain one extra element, so the median is simply the maximum element on the left side. For even total length, both sides still differ by at most one, and the median becomes the average of the two middle boundary values.

This is why the formula is (m + n + 1) / 2 and not just (m + n) / 2. Without the +1, odd-length cases would place the median on the wrong side of the partition.

The binary search range is l = 0 to h = m, not m - 1. That is because the correct partition may take:

zero elements from A, or all elements from A.

Those are valid partitions, so both endpoints must be included. If you stop at m - 1, you lose the possibility that the entire smaller array belongs on the left side.

For a chosen cut cutA, the cut in B is forced:

cutB = leftSize - cutA

Then we inspect the four boundary values:

leftA = largest value on A's left side
rightA = smallest value on A's right side
leftB = largest value on B's left side
rightB = smallest value on B's right side

The partition is correct exactly when:

leftA <= rightB and leftB <= rightA

That means every element on the left is less than or equal to every element on the right. If leftA > rightB, the cut in A is too far right, so we move left. If leftB > rightA, the cut in A is too far left, so we move right.

Sentinel values are used at the boundaries:

INT_MIN stands for “nothing exists on the left”
INT_MAX stands for “nothing exists on the right”

They are not part of the data. They are just a clean way to avoid special-case branching when the partition touches either edge.

Fully Optimal Pseudocode

1. Let A be the smaller array.
2. leftSize = (m + n + 1) / 2
3. Binary search cutA in [0, m]
4. cutB = leftSize - cutA
5. Build boundary values:
      leftA  = (cutA == 0) ? -infinity : A[cutA - 1]
      rightA = (cutA == m) ? +infinity : A[cutA]
      leftB  = (cutB == 0) ? -infinity : B[cutB - 1]
      rightB = (cutB == n) ? +infinity : B[cutB]
6. If leftA <= rightB and leftB <= rightA:
      if total length is odd:
          answer = max(leftA, leftB)
      else:
          answer = (max(leftA, leftB) + min(rightA, rightB)) / 2
7. Else if leftA > rightB:
      move search left
8. Else:
      move search right

C++17 Code

double findMedianSortedArrays(vector<int>& nums1, vector<int>& nums2) {
    const vector<int>& A = (nums1.size() <= nums2.size()) ? nums1 : nums2;
    const vector<int>& B = (nums1.size() <= nums2.size()) ? nums2 : nums1;

    int m = (int)A.size();
    int n = (int)B.size();

    int leftSize = (m + n + 1) / 2;
    int l = 0, r = m;

    while (l <= r) {
        int cutA = l + (r - l) / 2;
        int cutB = leftSize - cutA;

        int leftA  = (cutA == 0) ? INT_MIN : A[cutA - 1];
        int rightA = (cutA == m) ? INT_MAX : A[cutA];
        int leftB  = (cutB == 0) ? INT_MIN : B[cutB - 1];
        int rightB = (cutB == n) ? INT_MAX : B[cutB];

        if (leftA <= rightB && leftB <= rightA) {
            if ((m + n) % 2 == 1) {
                return (double)max(leftA, leftB);
            }
            return ((double)max(leftA, leftB) + (double)min(rightA, rightB)) / 2.0;
        }
        else if (leftA > rightB) {
            r = cutA - 1;
        }
        else {
            l = cutA + 1;
        }
    }

    return 0.0;
}

Dry Run 1 — Odd Total

Input: A = [1, 3], B = [2]
After size check: A becomes [2], B becomes [1, 3]
leftSize: (1 + 2 + 1) / 2 = 2

Step 1: l = 0, r = 1, cutA = 0, cutB = 2
leftA = -infinity, rightA = 2, leftB = 3, rightB = +infinity
Check: leftB > rightA, so cutA is too far left
Action: move right, l = 1

Step 2: cutA = 1, cutB = 1
leftA = 2, rightA = +infinity, leftB = 1, rightB = 3
Check: leftA <= rightB and leftB <= rightA
Action: partition is correct
Result: total length is odd, so median = max(2, 1) = 2

Dry Run 2 — Even Total

Input: A = [1, 2], B = [3, 4]
leftSize: (2 + 2 + 1) / 2 = 2

Step 1: cutA = 1, cutB = 1
leftA = 1, rightA = 2, leftB = 3, rightB = 4
Check: leftB > rightA, so cutA is too far left
Action: move right, l = 2

Step 2: cutA = 2, cutB = 0
leftA = 2, rightA = +infinity, leftB = -infinity, rightB = 3
Check: partition is correct
Result: median = (max(2, -infinity) + min(+infinity, 3)) / 2 = (2 + 3) / 2 = 2.5

Dry Run 3 — Extreme Edge Case

Input: A = [], B = [1]
leftSize: (0 + 1 + 1) / 2 = 1
Step: cutA = 0, cutB = 1
leftA = -infinity, rightA = +infinity, leftB = 1, rightB = +infinity
Check: partition is correct immediately
Result: median = max(-infinity, 1) = 1

This edge case is exactly why the boundary sentinels matter. Without them, the code would need special branches for empty sides, which makes the logic harder to trust and easier to break.

Why the code works

The binary search is not searching for a value. It is searching for a partition point. The partition is valid when the largest item on the left side of one array is not greater than the smallest item on the right side of the other array, and vice versa. Since the arrays are sorted, this condition is enough to guarantee every left-side element is less than or equal to every right-side element.

We always search the smaller array because that keeps the search range minimal and guarantees that the cut in the other array remains well-defined.

Duplicates are handled naturally because the condition uses <=, not strict <. Negative numbers also work without any special handling, because the method depends only on ordering.

One practical implementation detail: when computing the even-length median, cast to double before adding the two boundary values. That avoids integer overflow in edge cases where the boundary values are very large.

Complexity of the fully optimal solution

Time Complexity: O(log min(m, n)). We binary search only the smaller array, and each iteration discards half of the remaining search space.

Space Complexity: O(1). Only a handful of variables are used.

Algorithm Name: Binary Search on Partition / Median of Two Sorted Arrays partition method.

Final Interview Signal

The moment you see two sorted arrays and a question about the median or k-th rank, think about partitioning the arrays rather than merging them. That is the pattern this problem is designed to test.
