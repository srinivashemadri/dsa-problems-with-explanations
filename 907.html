LeetCode 907 — Sum of Subarray Minimums

Step 1 — Problem Statement

Input: You are given an integer array arr. For every contiguous subarray, you must find its minimum element. The task is to compute the sum of those minimums across all subarrays.

Output: Return that total sum, usually modulo 1,000,000,007 because the answer can become very large.

Key Constraints: The array can be large enough that an O(n2) or O(n3) approach becomes too slow. The values are positive, but duplicates are allowed, which is the part that breaks many clean-looking solutions. Because the final answer can exceed 32-bit integer range, the implementation must use 64-bit arithmetic before applying modulo.

Edge Cases: A single-element array, all elements equal, strictly increasing arrays, strictly decreasing arrays, and arrays with repeated minimum values are the cases that matter most. The duplicate case is especially tricky because one subarray minimum can be “claimed” by two equal elements unless tie-breaking is handled carefully.

Step 2 — Problem Understanding & Approach Overview

This is not really a “scan every subarray” problem. It is a contribution-counting problem. Instead of asking, “What is the minimum of this subarray?”, the better question is, “How many subarrays treat this element as their minimum?”

The core challenge is to avoid recomputing the minimum from scratch for each subarray. The problem category is monotonic stack + contribution technique. The mental model should be: every element owns a block of subarrays where it is the smallest value, and the size of that block is determined by the nearest smaller element on the left and the nearest smaller-or-equal element on the right.

The subtle trap is duplicates. If you use the same comparison rule on both sides, equal values will either be counted twice or missed. A correct solution must break ties consistently on only one side.

Step 3 — Brute Force Solution

The most naive solution is to enumerate every subarray and compute its minimum independently. That is the cleanest starting point, but it is far too slow. 

for i from 0 to n - 1:
    for j from i to n - 1:
        minValue = +infinity
        for k from i to j:
            minValue = min(minValue, arr[k])
        answer += minValue

Time Complexity: O(n3) because there are O(n2) subarrays and each one recomputes the minimum by scanning the range again.

Space Complexity: O(1), because no extra data structure is required beyond a few variables.

Performance Bottleneck: The same subarray values are inspected again and again. The minimum for overlapping ranges is recomputed repeatedly instead of being reused.

Step 4 — Intuition Building
Test Case 1

Input: 7

One element means only one subarray exists: [7]. There is nothing to compare against, so the element is automatically the minimum.

Action: Count that single subarray.

Result: 7

This case shows the base behavior: an element always contributes at least once, because every element is the minimum of the subarray containing only itself.

Test Case 2

Input: 3 1 2 4

The subarrays are many, but the key observation is that the value 1 is very powerful: it becomes the minimum for every subarray that includes it and does not extend past a smaller value on either side. Since nothing is smaller than 1, it gets a wide range of ownership.

Action: Think in terms of ownership blocks. For the element 1, the previous smaller element does not exist, and the next smaller element does not exist. That means it can extend across the full left and right freedom inside the array.

Result: 1 contributes to many subarrays, not just one. This is the discovery: you do not need to inspect every subarray separately if you can count how far each element can expand before a smaller value blocks it.

In this array, every element’s contribution can be written as: 

contribution of arr[i] = arr[i] * (# choices on left) * (# choices on right)

That is the shape of the optimized solution.

Test Case 3 (Duplicate Edge Case)

Input: 2 2

The subarrays are [2], [2], and [2 2]. The subarray [2 2] has the same minimum value from both positions, so a naive “count all possible minima” idea would double count it.

Action: Break ties consistently. One valid rule is: use previous strictly smaller on the left and next smaller-or-equal on the right. Then equal values are assigned to one side only, so each subarray is counted exactly once.

Result: No double counting. The rightmost equal element can own the tied subarray, and the left equal element stops before overlapping ownership.

This is the exact signal that should make you think of the same approach in future problems: whenever you need the sum of a local extremum over all subarrays, think monotonic stack + contribution counting.

Step 5 — Optimized Solution 1 (Intermediate)

The first useful optimization is to avoid re-scanning every subarray from scratch. While expanding a subarray end by end, keep track of the running minimum. That immediately removes one nested scan. 

for i from 0 to n - 1:
    currentMin = +infinity
    for j from i to n - 1:
        currentMin = min(currentMin, arr[j])
        answer += currentMin

What was eliminated: the inner recomputation of the minimum for each subarray. Once a subarray is extended by one element, its minimum can be updated in O(1).

Time Complexity: O(n2) because there are O(n2) subarrays, and each extension now updates the minimum in constant time.

Space Complexity: O(1).

This version is still too slow for the largest inputs, but it builds the bridge from brute force to the real insight.

Step 5 — Optimized Solution 2 (Best Known / Fully Optimal)

Algorithm: Monotonic increasing stack + contribution counting.

The key insight is this: for each element arr[i], count how many subarrays choose arr[i] as their minimum. If the previous strictly smaller element is at index p, and the next smaller-or-equal element is at index q, then:

Left choices = i - p
Right choices = q - i
Contribution = arr[i] × Left choices × Right choices 

int sumSubarrayMins(vector<int>& arr) {
    const int MOD = 1'000'000'007;
    int n = (int)arr.size();
    vector<long long> left(n), right(n);
    stack<int> st;

    // Previous strictly smaller element
    for (int i = 0; i < n; ++i) {
        while (!st.empty() && arr[st.top()] >= arr[i]) st.pop();
        int prevLess = st.empty() ? -1 : st.top();
        left[i] = i - prevLess;
        st.push(i);
    }

    while (!st.empty()) st.pop();

    // Next smaller-or-equal element
    for (int i = n - 1; i >= 0; --i) {
        while (!st.empty() && arr[st.top()] > arr[i]) st.pop();
        int nextLessOrEqual = st.empty() ? n : st.top();
        right[i] = nextLessOrEqual - i;
        st.push(i);
    }

    long long ans = 0;
    for (int i = 0; i < n; ++i) {
        ans = (ans + (left[i] * right[i] % MOD) * arr[i]) % MOD;
    }

    return (int)ans;
}

The reason for using >= on the left pass and > on the right pass is tie-breaking. Equal elements must not both claim the same subarray. This convention assigns tied ownership to the rightmost equal element. A symmetric alternative also works, but the two sides must not use the same strictness.

The duplicate is the important part. The tie-break rule ensures the subarray [2 2] is counted once, not twice. 

Left pass:
i = 0 -> left[0] = 1
i = 1 -> pop index 0 because arr[0] >= arr[1]
         prevLess = -1
         left[1] = 2

Right pass:
i = 1 -> right[1] = 1
i = 0 -> nextLessOrEqual = 1
         right[0] = 1

Contributions

arr[0] = 2 -> 2 * 1 * 1 = 2
arr[1] = 2 -> 2 * 2 * 1 = 4

Total = 6

This matches the three subarrays: [2], [2], and [2 2], whose minimums are 2, 2, and 2.

Why This Works

Every subarray has exactly one representative minimum under the tie-breaking rule. For each index i, the left boundary can move anywhere after the previous smaller element, and the right boundary can move anywhere before the next smaller-or-equal element. Those choices are independent, so the count is the product of the two spans.

Handling the Tricky Parts

Why previous strictly smaller? Because it gives a clean left boundary that stops only when a genuinely smaller value appears.

Why next smaller-or-equal? Because equal values need a deterministic owner. Allowing equality only on one side prevents double counting.

Why long long? The number of subarrays can be large, and multiplying span lengths by the value can exceed 32-bit range before modulo is applied.

Complexity Analysis

Time Complexity: O(n). Each index is pushed and popped at most once in each stack pass, so the total work stays linear.

Space Complexity: O(n) for the left/right arrays and the stack.

Interview Signal to Remember

Whenever a problem asks for the sum of minimums or maximums over all subarrays, do not start by enumerating subarrays. Think instead: Can I count how many subarrays each element owns as the extremum? If the answer is yes, a monotonic stack is usually the right tool.
