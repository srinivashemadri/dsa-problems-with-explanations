LeetCode 496 — Next Greater Element I
Step 1 — Problem Statement

Input: You are given two integer arrays, nums1 and nums2. Every element of nums1 appears in nums2, and all values are distinct. For each element in nums1, you must find its next greater element in nums2 — that is, the first number to its right in nums2 that is strictly larger.

Output: Return an array where each position corresponds to the next greater element of the same-valued element in nums1. If no greater element exists to the right in nums2, return -1 for that element.

Key Constraints: The important part is not just finding a greater number, but finding the first greater number to the right. Also, the elements are distinct, which makes value-to-answer mapping safe.

Edge Cases: a single-element array, a strictly increasing array, a strictly decreasing array, an element that is already the maximum in nums2, and a case where the next greater element does not exist at all. If the problem were generalized beyond LeetCode's constraints, duplicates would be a major complication, but here distinct values remove that trap.

Step 2 — Problem Understanding & Approach Overview

Strip away the story: for each queried value from nums1, you need the next greater value in the relative order of nums2. This is a classic Next Greater Element problem.

The core challenge is to avoid scanning the right side again and again for every element.

Category: Monotonic Stack + Hash Map.

Mental Model: Scan nums2 from left to right while maintaining a stack of values that are still waiting for a greater number. The stack should stay in decreasing order. Whenever a new number is bigger than the top of the stack, that new number is the next greater element for the stack top.

Subtle Trap: Many candidates either do a nested scan for each element, which is too slow, or they try to compute the answer only for nums1 directly and miss the fact that it is much easier to preprocess all of nums2 once. Another common mistake is forgetting that the answer must be the first greater element to the right, not just any greater element.

Step 3 — Brute Force Solution

The naive idea is straightforward: for each number in nums1, first locate it in nums2, then scan to the right until a greater number is found. 

for each x in nums1:
    find index of x in nums2
    ans = -1
    for j from index + 1 to end of nums2:
        if nums2[j] > x:
            ans = nums2[j]
            break
    store ans in result

Why it works: The inner scan checks numbers in exact right-side order, so the first number greater than x is necessarily the correct next greater element.

Time Complexity: O(n × m). For each element of nums1, you may scan most of nums2 to find its position and then scan again to the right. In the worst case, this becomes quadratic.

Space Complexity: O(1) extra space, ignoring the output array.

Bottleneck: Repeating right-side scans for every query wastes work. The same comparisons are being redone many times.

Step 4 — Intuition Building

The key discovery is that nums2 can be processed once, and every number can be assigned its next greater value at the moment a bigger number appears.

Test Case 1

Input: nums1 = 2 4
       nums2 = 1 2 3 4
    Observation: values keep increasing
    Current stack: waiting elements in decreasing order

Action:
    1 arrives  - stack = [1]
    2 arrives  - 2 > 1, so next greater of 1 is 2
                 stack = [2]
    3 arrives  - 3 > 2, so next greater of 2 is 3
                 stack = [3]
    4 arrives  - 4 > 3, so next greater of 3 is 4
                 stack = [4]

Result mapping:
    1 -> 2
    2 -> 3
    3 -> 4
    4 -> -1

Final answer for nums1:
    2 -> 3
    4 -> -1

Test Case 2

Input: nums1 = 4 1 2
       nums2 = 1 3 4 2
    Observation: some elements never find a greater value
    Important: the answer must be the first greater element to the right

Action:
    1 arrives  - stack = [1]
    3 arrives  - 3 > 1, so next greater of 1 is 3
                 stack = [3]
    4 arrives  - 4 > 3, so next greater of 3 is 4
                 stack = [4]
    2 arrives  - 2 is not greater than 4
                 stack = [4, 2]

End of scan:
    4 has no greater element to the right -> -1
    2 has no greater element to the right -> -1

Final answer for nums1:
    4 -> -1
    1 -> 3
    2 -> -1

Test Case 3 (Edge Case)

Input: nums1 = 1
       nums2 = 5 4 3 2 1
    Observation: strictly decreasing array
    Every new number is smaller than the previous one
    This is the worst case for brute force if repeated many times

Action:
    5 arrives  - stack = [5]
    4 arrives  - 4 is not greater than 5, stack = [5, 4]
    3 arrives  - stack = [5, 4, 3]
    2 arrives  - stack = [5, 4, 3, 2]
    1 arrives  - stack = [5, 4, 3, 2, 1]

End of scan:
    nobody gets a greater element
    every remaining number maps to -1

Result:
    1 -> -1

The pattern is now visible: each number is waiting for the first bigger number that appears later. A decreasing stack stores exactly those waiting values.

What to notice for future problems: Whenever a problem asks for the next greater/smaller, first element to the right/left, or nearest dominating value in order, your instinct should immediately go to a monotonic stack.

Step 5 — Optimized Solution

There is one best-known optimization here: preprocess nums2 once using a monotonic decreasing stack, and store the answer for every value in a hash map. Then answer each query from nums1 in O(1).

Why this is fully optimal for the problem: Every element of nums2 is pushed once and popped once, so the preprocessing is linear. Since nums1 is just a subset query, a hash lookup is the cleanest final step.

Optimized Solution — Pseudocode

create empty stack
create empty map valueToNextGreater

for each num in nums2:
    while stack is not empty and num > stack.top():
        valueToNextGreater[stack.top()] = num
        pop stack
    push num onto stack

while stack is not empty:
    valueToNextGreater[stack.top()] = -1
    pop stack

for each x in nums1:
    answer.push_back(valueToNextGreater[x])

Interview-Ready C++17 Code

vector nextGreaterElement(vector& nums1, vector& nums2) {
    unordered_map nextGreater;
    stack st;

    for (int num : nums2) {
        while (!st.empty() && num > st.top()) {
            nextGreater[st.top()] = num;
            st.pop();
        }
        st.push(num);
    }

    while (!st.empty()) {
        nextGreater[st.top()] = -1;
        st.pop();
    }

    vector ans;
    ans.reserve(nums1.size());
    for (int x : nums1) {
        ans.push_back(nextGreater[x]);
    }

    return ans;
}

Dry Run on a Meaningful Test Case

Input:
    nums1 = 4 1 2
    nums2 = 1 3 4 2

Initial state:
    stack = empty
    map   = empty

Step 1: num = 1
    stack is empty
    push 1
    stack = [1]

Step 2: num = 3
    3 > 1, so 1's next greater is 3
    pop 1
    push 3
    stack = [3]
    map = { 1: 3 }

Step 3: num = 4
    4 > 3, so 3's next greater is 4
    pop 3
    push 4
    stack = [4]
    map = { 1: 3, 3: 4 }

Step 4: num = 2
    2 is not greater than 4
    push 2
    stack = [4, 2]
    map = { 1: 3, 3: 4 }

End of nums2:
    2 has no greater element -> -1
    4 has no greater element -> -1
    map = { 1: 3, 3: 4, 2: -1, 4: -1 }

Answer nums1:
    4 -> -1
    1 -> 3
    2 -> -1

Final result:
    -1 3 -1

How this handles the edge case from Step 4: In a strictly decreasing array like 5 4 3 2 1, nothing ever pops while scanning. Every value stays on the stack until the end, and all of them correctly get -1. That is exactly the right behavior, with no special-case logic needed.

Time Complexity: O(n + m). Each value in nums2 is pushed once and popped once, so the stack work is linear. Then each query in nums1 is answered in O(1) average time using the hash map.

Space Complexity: O(m). The stack and hash map can each hold up to all values from nums2. The output array adds O(n), which is required.

Algorithm Name: Monotonic Decreasing Stack + Hash Map.

Final Interview Takeaway

The real insight is not “use a stack” in the abstract. It is: as soon as a larger number appears, it resolves every smaller unresolved number before it. That is why the decreasing stack works so naturally.

When you see a future problem asking for the next greater/smaller element, the first thing to ask yourself is: Can I process the array once and resolve waiting elements as soon as a better candidate appears? If yes, you are probably looking at a monotonic stack problem.
