LeetCode 155 — Min Stack

Step 1 — Problem Statement

Input: You are asked to design a stack that supports the usual stack operations, especially push, pop, top, and getMin. The stack stores integers.

Output: After each operation, the structure must behave like a normal stack, and getMin must return the smallest element currently present in the stack in constant time.

Key Constraints: The real constraint is not just correctness, but time. push, pop, top, and getMin should all be handled in O(1) time. That immediately rules out rescanning the entire stack every time you need the minimum. The usual LeetCode contract assumes the operations are called validly.

Edge Cases: A single element stack, duplicate minimum values, strictly increasing input, strictly decreasing input, negative values, and popping until the stack becomes empty all matter. The subtle one is duplicate minima: if the current minimum is removed, the data structure must still remember the previous minimum.

Step 2 — Problem Understanding & Approach Overview

This problem is really asking for a stack with memory of the minimum-so-far history. The story is just packaging; the algorithmic challenge is to answer a range-like query, getMin, instantly while the data changes over time.

The core category is data structure design, specifically a stack augmented with auxiliary state.

The mental model is simple: every time a new element arrives, ask, “Does this change the minimum?” If yes, record that change somewhere. If no, keep the existing minimum unchanged. The common mistake is to store only the current minimum value and forget how to restore the old one after popping it.

Step 3 — Brute Force Solution

The naive idea is to store all elements in one stack or array. push, pop, and top are easy. But getMin would scan the entire structure each time.

push(x):
    stack.append(x)

pop():
    stack.pop()

top():
    return stack[-1]

getMin():
    ans = +infinity
    for value in stack:
        ans = min(ans, value)
    return ans

Time Complexity: push, pop, and top are O(1). getMin is O(n) because it inspects every element. If you call getMin repeatedly, the total cost becomes expensive very quickly.

Space Complexity: O(n) for storing the stack itself.

Bottleneck: The expensive part is repeatedly recomputing the minimum from scratch. That work is avoidable because the minimum changes in a very structured way.

Step 4 — Intuition Building

Test Case 1

Input: push(5), getMin(), top(), pop()

    Current state: only one element exists, so the minimum is trivially 5

Action: Every query is immediate, because there is nothing to compare against

Result: getMin = 5, top = 5

Test Case 2

Input: push(5), push(3), push(7), getMin(), pop(), getMin()

    Current state: the minimum changes when 3 arrives, then stays 3 after 7 arrives

Action: A brute-force solution would rescan 3 elements on every getMin

Result: getMin = 3, and after popping 7, the minimum is still 3

    Insight: the minimum only changes when a new smaller value arrives or when the current minimum is removed. That means you do not need to rescan the whole stack; you only need a history of minimum changes.

Test Case 3 (Edge Case)

Input: push(2), push(2), push(1), pop(), getMin()

    Current state: duplicate minima exist before 1 arrives

Action: If you only remember the latest minimum, popping 1 must restore the previous minimum 2 correctly

Result: getMin = 2

    Signal for future problems: when a query asks for an aggregate like minimum or maximum repeatedly over a changing stack, think about preserving the history of extrema rather than recomputing them.

Step 5 — Optimized Solution 1 (Intermediate)

The first real optimization is to keep a second stack that stores the minimum seen so far at each depth. The main stack stores values, and the min stack stores a non-increasing sequence of minima.

On push(x), push x onto the main stack. If the min stack is empty or x <= minStack.top(), also push x onto the min stack. On pop(), pop from the main stack, and if the removed value equals minStack.top(), pop the min stack too. Then top() reads from the main stack, and getMin() reads from the min stack.

push(x):
    main.push(x)
    if minStack is empty or x <= minStack.top():
        minStack.push(x)

pop():
    x = main.top()
    main.pop()
    if x == minStack.top():
        minStack.pop()

top():
    return main.top()

getMin():
    return minStack.top()

Time Complexity: Every operation is O(1). The min stack removes the need to scan the full stack.

Space Complexity: O(n) in the worst case, because the min stack may store many elements, for example in a strictly decreasing sequence.

What was eliminated: The full scan on every getMin. The price paid is an extra stack that mirrors the minimum history.

Step 5 — Optimized Solution 2 (Best Known / Fully Optimal)

The further insight is that you do not actually need a second stack. You can encode “new minimum” information directly inside the values stored in one stack.

Keep one stack and one variable mn for the current minimum. When a new value x is at least the current minimum, store it normally. When x is smaller than the current minimum, store a special encoded number 2*x - mn, then update mn = x. That encoded number is guaranteed to be smaller than the new minimum, so it acts like a marker.

On pop, if the top value is smaller than mn, it means the top is an encoded marker, not the real value. In that case, the real top value is the current minimum, and the previous minimum can be restored by oldMn = 2*mn - encodedTop.

Why this works: The encoded number preserves enough information to recover both the popped minimum and the previous minimum. So the stack keeps the order of elements and the minimum history at the same time.

Why not just store the minimum value once? Because after popping the minimum, you would lose the previous minimum. That is the exact bug the encoded trick fixes.

class MinStack {
    stack<long long> st;
    long long mn;

public:
    MinStack() : mn(0) {}

    void push(int val) {
        long long x = val;
        if (st.empty()) {
            st.push(x);
            mn = x;
            return;
        }

        if (x >= mn) {
            st.push(x);
        } else {
            st.push(2LL * x - mn);
            mn = x;
        }
    }

    void pop() {
        long long t = st.top();
        st.pop();

        if (st.empty()) {
            mn = 0;
            return;
        }

        if (t < mn) {
            mn = 2LL * mn - t;
        }
    }

    int top() {
        long long t = st.top();
        if (t < mn) return (int)mn;
        return (int)t;
    }

    int getMin() {
        return (int)mn;
    }
};

Dry Run:

Input: push(5), push(3), push(7), top(), getMin(), pop(), getMin(), pop(), getMin()

    Step 1 — push(5): stack = [5], mn = 5

    Step 2 — push(3): 3 < 5, so store encoded value 2*3 - 5 = 1; stack = [5, 1], mn = 3

    Step 3 — push(7): 7 >= 3, store normally; stack = [5, 1, 7], mn = 3

    Step 4 — top(): top is 7, which is not smaller than mn, so answer = 7

    Step 5 — getMin(): answer = 3

    Step 6 — pop(): remove 7, stack = [5, 1], mn stays 3

    Step 7 — getMin(): answer = 3

    Step 8 — pop(): remove 1, and since 1 < mn, it is an encoded marker. Restore previous minimum: mn = 2*3 - 1 = 5; stack = [5]

    Step 9 — getMin(): answer = 5

Extreme Edge Case: If all values are identical, for example push(4), push(4), push(4), every value is stored normally, and getMin() always returns 4. If the stack becomes empty and later receives new values, the empty check in push() re-initializes the minimum correctly.

Time Complexity: push, pop, top, and getMin are all O(1). The encoded arithmetic is constant time.

Space Complexity: O(n) for the single stack, with only one extra variable for the current minimum.

Algorithm Name: This is the encoded stack or single-stack min encoding technique.

Final Interview Takeaway: The moment a problem repeatedly asks for the minimum of a structure that changes over time, think about caching the minimum history. First, a second stack gives the cleanest explanation. Then, if you want the memory-tight version, encode the minimum changes inside the stack itself.
