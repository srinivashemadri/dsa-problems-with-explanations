LeetCode 56 — Merge Intervals
Step 1 — Problem Statement

Input: a list of intervals, where each interval is written as [start, end]. The intervals are not guaranteed to be sorted, and they may overlap or even just touch at endpoints.

Output: a new list of intervals after merging every overlapping or touching interval into the smallest possible set of disjoint intervals.

Key Constraints: the relative order of the original input does not matter, so sorting is allowed; two intervals should be merged whenever the next interval starts at or before the current merged interval ends; the final answer must contain non-overlapping intervals only.

Edge Cases: empty input, one interval, already disjoint intervals, fully nested intervals, touching intervals like [1,4] and [4,5], completely overlapping intervals, and intervals given in unsorted order.

Step 2 — Problem Understanding & Approach Overview

This problem is really asking for the union of many closed intervals. The story is just a disguise; the core challenge is deciding, after ordering intervals by start time, when the current interval should extend the previous merged range and when it should begin a new one.

The category is sorting + greedy interval processing. The mental model is simple: after sorting, walk left to right while maintaining one “active merged interval.” Every new interval either stretches that active interval or becomes the next separate block.

The subtle trap is forgetting that touching endpoints must merge in this problem, so the condition is not just “start < end” but effectively start ≤ currentEnd. Another common mistake is trying to merge without sorting first.

Step 3 — Brute Force Solution

A naive way is to repeatedly compare every interval with every other interval, merge any pair that overlaps, and keep repeating until no more merges happen. 

Brute Force Pseudocode:

repeat
    mergedSomething = false
    for each interval i
        for each interval j after i
            if i and j overlap
                merge them into one interval
                remove the old two intervals
                mergedSomething = true
                break and restart scanning
until mergedSomething is false

return the final list

The reason this is slow is that every merge can force another full scan. In the worst case, many intervals keep collapsing one step at a time.

Time Complexity: O(n2) to O(n3) depending on how the deletions and rescans are implemented. The bottleneck is repeated pairwise checking and repeated restarting.

Space Complexity: O(1) extra space if done in place, aside from storage for the output structure.

Step 4 — Intuition Building

Test Case 1

Input: 1 3, 2 6, 8 10, 15 18
    Unsorted? not needed for the intuition yet, but sorting by start keeps intervals in order
    Active interval starts as [1,3]
    Next interval [2,6] overlaps because 2 ≤ 3
Action: extend active interval to [1,6]
Result so far: [1,6]
Next interval: [8,10]
    No overlap because 8 > 6
Action: close [1,6] and start a new active interval [8,10]
Result so far: [1,6], [8,10]
Next interval: [15,18]
    No overlap again because 15 > 10
Action: close [8,10] and start [15,18]
Final Result: [1,6], [8,10], [15,18]

The key insight here is that once intervals are sorted, you never need to look backward beyond the last merged interval. That eliminates the repeated global rescanning from brute force.

Test Case 2

Input: 1 4, 4 5
    These intervals touch exactly at 4
    Since the intervals are closed, touching means they belong together
Action: merge them into one interval
Result: [1,5]

This is the edge case many people miss. If you use a strict comparison and treat only true overlap as mergeable, you will incorrectly keep these separate.

Test Case 3 (Edge Case)

Input: 3 2, 1 4, 2 3
    First sort them by start:
    [1,4], [2,3], [3,2] is not valid input format for intervals, so think of the real edge case as unsorted valid intervals like [5,7], [1,2], [2,4]
    After sorting: [1,2], [2,4], [5,7]
    Active interval [1,2]
    Next interval [2,4] touches at 2
Action: merge into [1,4]
    Next interval [5,7] does not overlap
Action: start a new block
Result: [1,4], [5,7]

The signal that should make you think of this approach immediately is: “intervals,” “merge,” “overlap,” “minimum number of disjoint ranges,” or “union of ranges.” Whenever the task is to compress overlapping ranges, sort first and sweep once.

Step 5 — Optimized Solution

This problem has one best practical solution: sort by start time and then do a single linear pass. That is the standard optimal approach.

Idea: sort the intervals by their starting point. Keep one result list. For each new interval, compare it with the last merged interval. If they overlap or touch, extend the last merged interval. Otherwise, append the new one. 

Optimized Pseudocode:

if intervals is empty:
    return empty list

sort intervals by start
result = [first interval]

for each interval from the second onward:
    if current.start ≤ result.last.end:
        result.last.end = max(result.last.end, current.end)
    else:
        append current to result

return result
Interview-Ready C++17 Code:

vector> merge(vector>& intervals) {
    if (intervals.empty()) return {};

    sort(intervals.begin(), intervals.end());

    vector> merged;
    merged.push_back(intervals[0]);

    for (int i = 1; i < (int)intervals.size(); ++i) {
        if (intervals[i][0] <= merged.back()[1]) {
            merged.back()[1] = max(merged.back()[1], intervals[i][1]);
        } else {
            merged.push_back(intervals[i]);
        }
    }

    return merged;
}

Dry Run:

Input: [1,3], [2,6], [8,10], [15,18]

Sort: already sorted

Initialize:
merged = [ [1,3] ]

Step 1: current = [2,6]
Pivot check: 2 ≤ 3
Action: merge
Update merged.back() to [1,6]
merged = [ [1,6] ]

Step 2: current = [8,10]
Pivot check: 8 > 6
Action: append as a new interval
merged = [ [1,6], [8,10] ]

Step 3: current = [15,18]
Pivot check: 15 > 10
Action: append as a new interval
Final Result = [ [1,6], [8,10], [15,18] ]

Time Complexity: O(n log n) because sorting dominates. The scan itself is O(n), so the total is O(n log n).

Space Complexity: O(1) extra space if the sort is done in place, excluding the output list. If the sorting implementation uses extra stack space internally, that is implementation-dependent.

Algorithm Name: sort + sweep / greedy interval merging.
